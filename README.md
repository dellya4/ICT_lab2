# ICT Lab 2 — REST API with Amazon SQS

## Описание проекта

Данный проект является продолжением лабораторной работы №1.

В первой лабораторной работе взаимодействие между клиентом и сервером было реализовано напрямую через TCP sockets и собственные команды `ECHO`, `TIME` и `QUIT`.

В этой лабораторной работе используется **REST API на Flask**. Клиент отправляет HTTP-запросы, а данные передаются в формате JSON.

Проект поддерживает следующие функции:

- `POST /echo` — возвращает переданное сообщение;
- `GET /time` — возвращает текущее время сервера;
- `POST /jobs` — создаёт новую задачу и отправляет её в очередь;
- `GET /jobs/<job_id>` — возвращает статус задачи и результат после её выполнения.

Для обработки долгих задач используется **Amazon SQS**.

API не выполняет задачу сразу. Оно создаёт уникальный `job_id`, отправляет сообщение в очередь Amazon SQS и возвращает клиенту HTTP-код `202 Accepted`.

Отдельная программа `worker.py` получает сообщения из очереди, имитирует длительную обработку, переводит текст в верхний регистр и сохраняет результат.

Общая схема работы:

```text
Client
   |
   | HTTP request
   v
Flask REST API
   |
   | POST /jobs
   v
Amazon SQS
   |
   v
worker.py
   |
   | processing
   v
results/<job_id>.json
```

# Вопросы

## 1. Как REST принципиально отличается от socket protocol из Lab 1? Что даёт то, что каждый запрос self-contained?

В Lab 1 использовалось прямое TCP-соединение между клиентом и сервером.
Соединение оставалось открытым, пока клиент не отправлял команду:

```text
QUIT
```

Мы также самостоятельно придумали протокол:

```text
ECHO
TIME
QUIT
```

В Lab 2 используется стандартный протокол **HTTP и REST API**.

Теперь запрос состоит из:

- HTTP-метода;
- URL;
- при необходимости JSON-данных.

Например:

```text
POST /echo
```

с JSON:

```json
{
  "message": "hello"
}
```

Каждый REST-запрос является **self-contained**, то есть самостоятельным. Он содержит всю информацию, которая нужна серверу для его обработки.

Серверу не нужно помнить предыдущие запросы клиента.

Это даёт несколько преимуществ:

- сервер становится проще;
- запросы легче тестировать;
- систему легче масштабировать;
- можно запустить несколько копий API;
- следующий запрос клиента может обработать другой сервер.

## 2. Почему endpoint отправки задачи возвращает `202`, а не `200`?

Когда клиент отправляет:

```text
POST /jobs
```

задача ещё не выполнена.

API только:

1. принимает запрос;
2. создаёт `job_id`;
3. отправляет задачу в Amazon SQS;
4. сообщает клиенту, что задача принята.

После этого задачу отдельно выполняет `worker.py`.

Поэтому используется:

```text
202 Accepted
```

Этот код означает:

> Запрос принят для обработки, но обработка ещё не закончена.

Код:

```text
200 OK
```

больше подходит для ситуации, когда операция уже успешно выполнена и результат готов.

## 3. Зачем вообще нужна очередь, если можно выполнить задачу прямо внутри HTTP-запроса?

Если задача выполняется быстро, её действительно можно выполнить прямо внутри запроса.

Но некоторые операции могут занимать долгое время.

Например:

- обработка большого файла;
- обработка изображения или видео;
- Machine Learning;
- создание большого отчёта;
- отправка большого количества писем;
- сложные вычисления.

Без очереди клиенту пришлось бы ждать:

```text
Client
   |
   | request
   v
Server
   |
   | long processing...
   |
   v
response
```

Если задача занимает 30 секунд, клиент будет ждать 30 секунд.

С очередью работа происходит иначе:

```text
Client
   |
   | POST /jobs
   v
API
   |
   v
Amazon SQS
   |
   | 202 Accepted
   v
Client
```

Клиент быстро получает ответ и может продолжить работу.

Позже:

```text
Amazon SQS
   |
   v
Worker
   |
   v
Processing
```

Worker выполняет задачу независимо от HTTP-запроса.
Это также помогает при большом количестве задач. Они могут ждать в очереди и обрабатываться постепенно.

## 4. Что произойдёт, если worker упадёт после получения сообщения, но до удаления его из очереди?

Когда worker получает сообщение из Amazon SQS, сообщение не удаляется сразу.

Оно временно становится невидимым для других workers. Это называется **Visibility Timeout**.

Правильная последовательность:

```text
получить сообщение
        ↓
обработать
        ↓
сохранить результат
        ↓
удалить сообщение из SQS
```

Если worker успешно завершил работу, он вызывает удаление сообщения.

Но представим ситуацию:

```text
получить сообщение
        ↓
начать обработку
        ↓
WORKER CRASH
```

Worker не успел удалить сообщение.

В таком случае после окончания Visibility Timeout Amazon SQS снова сделает сообщение доступным.

Другой worker или тот же worker после перезапуска сможет получить его и выполнить задачу ещё раз.

Таким образом, задача не потеряется.

Однако есть возможность, что одна задача будет обработана повторно.

Поэтому в реальных распределённых системах важно проектировать обработку так, чтобы повторное выполнение одной задачи не приводило к серьёзным ошибкам.
